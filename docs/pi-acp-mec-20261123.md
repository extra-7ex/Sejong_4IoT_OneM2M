# Pi ACP와 MEC 복구 확인 (2026-11-23)

아래는 팀 Pi에서 확인한 운영 스냅샷이다. 다른 설치에 자동 적용되는 기본 설정이 아니며, 전체 시스템의 최소 권한이나 산업용 안전 성능을 입증하지 않는다. 실주소·자격증명은 기록하지 않는다.

## 필요한 권한과 실행 주체

| 대상 | 주체 | Pi에서 확인한 권한 |
|---|---|---|
| forklift `radar` CNT | `Criskengine`, `CVisionAI` | RETRIEVE(2) |
| Vision `fusedTracks` CNT | `Criskengine`, `CmecIPE` | 각각 RETRIEVE(2) |
| RiskEngine `events` CNT | `Criskengine` | CREATE + RETRIEVE(3) |
| IPE Vision `status` CNT | `CmecIPE` | CREATE + RETRIEVE(3) |
| radar 및 events CNT | `Cbridge` | RETRIEVE(2) |
| radar, fusedTracks, events, forklift alert, IPE status | IN 원격 Origin `/id-in/Cdashboard` | RETRIEVE(2) |
| 경보 그룹 `macp`, forklift·zone alert ACP | `Criskengine` | CREATE(1) |

소유자와 다른 기존 허용 규칙은 별도다. 작업자 운영 `alert`와 `status`는 기존 ACP를 공유하고 당시 `Criskengine`과 `CAdmin`에 35가 남아 있었다. 새 펌웨어가 이미 존재하는 ACP를 자동으로 수정하지는 않는다. 신규 작업자 ACP에서도 `alert`·`status`가 같은 정책을 쓰므로 리소스별 최소 권한은 후속 작업이다. 그룹의 실제 멤버와 `macp`는 작업자 재등록·전원 이동 후 재조회한다.

격리 CNT에서 허용 요청과 불필요한 생성·수정·삭제·탐색의 거부를 시험했다. 실제 Pi에서는 권한 축소 후 엔진의 WARNING·DANGER·SAFE `events` 생성 응답 HTTP 201/RSC 2001과 IPE 상태 CIN 기록을 확인했다. 이력 브리지의 전용 Origin 전환 후 새 WARNING·SAFE의 IN 기록도 확인했다. ACP에서 Origin별 권한을 설정한 것과 통신 상대의 신원 인증은 별개다.

## 서비스 설정과 복구

기존 CNT의 `acpi`와 기존 ACP의 `pv`·`pvs`를 백업하고 보존한 뒤, IPE의 fusedTracks 조회용 ACP와 브리지의 radar·events 조회용 ACP를 추가했다. 브리지에는 MN용 AE `Cbridge`를 등록했다. 팀 Pi의 systemd drop-in은 다음 설정을 적용한다.

- `safezone-ipe.service.d/60-acp-reader.conf`: `IPE_READ_ORIGIN=CmecIPE`
- `safezone-bridge.service.d/60-acp-reader.conf`: `BRIDGE_MN_ORIGIN=Cbridge`

각 Origin이 실제 필요한 CNT에 접근할 수 있는지 확인하기 전에 기존 서비스의 Origin을 전환하지 않는다. IN 이력 생성 측의 Origin은 별도다. 저장소의 기본 systemd 템플릿과 실제 Pi drop-in은 다르며, 새 설치에서 위 ACP가 자동으로 생성된다는 뜻이 아니다. 실패 시 기존 `acpi`·ACP 백업과 원래 서비스 설정으로 복구하고 기록·조회 경로를 확인한다.

## 그룹과 지게차 재연결 확인

작업자 무선 재연결 후 현재 alert RI가 `mid`에 남고 세 멤버와 `cnm=3`이 일치하는 것을 확인했다. 이후 MN-CSE가 SEGV로 종료·자동 재시작한 뒤 세 `mid`는 유지됐지만 `cnm=2`로 다시 조회됐다. 같은 날 격리 tinyIoT에서도 그룹을 2개에서 3개로 갱신한 다음 CSE를 재시작하자 `mid=3`, `cnm=2`가 재현됐다. Pi 소스에서는 그룹 갱신 시 메모리의 `cnm`을 바꾸지만 DB 갱신에는 요청 객체를 넘기는 코드가 있어 관련 가능성이 있다. 두 빌드의 정확한 원인과 SEGV의 원인은 별도 확인이 필요하며, 영구 수정 또는 Pi 재시작 시험은 하지 않았다.

`cnm=2`, `mid=3`인 상태에서도 실제 엔진 DANGER가 세 alert CNT에 기록된 것을 확인했다. 이는 모든 fan-out 조건에서 정상 동작한다는 보장은 아니다. 지게차 ESP의 주소 변경 시 기존 SUB의 `nu`만 갱신하고 RI·`nct`·`enc`를 보존했다. 사용자가 지게차 부저와 DANGER 시 포크 정지를 확인했다. DHCP 환경에서는 다음 재연결 때 주소를 다시 확인한다.

MEC Redis·플랫폼·프록시 컨테이너에는 `unless-stopped` 재시작 정책을 설정했다. Redis 저장본을 별도 백업하고 세 컨테이너를 직접 순차 재시작했을 때 기존 수동 등록 서비스의 ID·주소가 유지되고 IPE가 새 상태 CIN을 기록했다. 노트북 격리 컨테이너의 오류 종료 후 자동 재시작도 확인했다. Pi 전체 재부팅 시 컨테이너 준비 순서와 IPE 복구, 비정상 전원 차단 후 Redis의 최신 데이터 보존은 확인하지 않았다. 등록부의 `ACTIVE`와 실제 Vision 데이터 신선도는 별도이며, 기록 당시 Vision은 중지돼 IPE 데이터 상태가 `INACTIVE`였다.

MN-CSE는 노트북 IN에 처음 등록하지 못하면 기동을 반복하던 문제가 별도로 확인됐다. MEC 컨테이너 재시작 설정으로 이 문제가 해결되는 것은 아니다. 작업자 부저는 UNKNOWN에서 무음으로 유지하며 SAFE와의 내부 상태 표현 구분은 [후속 항목](worker-unknown-follow-up.md)이다.
