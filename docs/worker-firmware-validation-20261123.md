# 작업자 ESP8266 등록 수정 및 검증 결과

2026-11-23 실장비 시험 기록. 펌웨어 변경 커밋은 `2dfe2ef`이며, 이 문서는 당시 검증 결과를 공유하기 위한 요약이다. 이후 Pi에서 수행한 별도 권한 변경까지 재검증했다는 의미는 아니다. 비밀번호, 로컬 설정, 실주소, 원시 장치 로그와 바이너리는 공유 자료에 포함하지 않는다.

## 변경 파일과 동작

| 파일 | 변경 |
|---|---|
| `esp8266/led_server/worker_node.ino` | AE 삭제 제거, 기존 등록 재사용, 현재 IP로 poa 갱신 및 성공 확인, 기존 CNT/SUB/ACP 조회·재사용, 신규 ACP 규칙 분리 |
| `docs/runbook.md` | 재등록·그룹 가입 절차를 현재 동작에 맞춰 설명 |
| `docs/worker-registration.md` | 등록·권한 경계, 별도 그룹 가입, 빌드·복구 절차 |
| `docs/worker-unknown-follow-up.md` | UNKNOWN 무음 정책 유지 및 상태 표현 구분 후속 항목 |

자동 등록은 유지한다. 기존 AE를 발견하면 삭제하지 않고 poa를 PUT한 뒤 AE-ID와 실제 poa를 조회해 확인한다. PUT 실패 또는 조회 불일치는 등록 실패로 처리하고 재시도한다. 기존 CNT의 acpi 및 SUB를 덮어쓰지 않으며, 기존 SUB의 수신처·생성 이벤트·nct가 예상과 다르면 등록을 중단한다. ACP 생성·조회와 status CIN 생성도 성공해야 등록 완료로 처리한다.

신규 ACP의 pv는 소유자 63, Criskengine CREATE(1), CAdmin 35로 분리하며 pvs는 기존 소유자 63을 유지한다. 기존 ACP의 POST 409는 정책 갱신이 아니다. 기존 pv/pvs는 조회·보고만 하고 변경하지 않는다.

## 빌드 및 시험

- 보드: NodeMCU 1.0 (ESP-12E Module), ESP8266EX, 4MB flash. 시리얼 heartbeat로 작업자 보드를 식별한 뒤 업로드했다.
- FQBN: `esp8266:esp8266:nodemcuv2`. Arduino CLI 1.6.0, ESP8266 core 3.1.2, ArduinoJson 7.4.3.
- 컴파일 및 업로드 성공. 업로드 해시 검증 성공. 운영용 빌드는 RAM 37%, 명령 RAM 92%, flash code 28%를 사용했다.
- 업로드 전 원본 전체 플래시와 원본 소스, 설정·리소스 스냅샷을 로컬에 보존했다. 전체 플래시와 펌웨어 바이너리에는 자격증명이 포함될 수 있으므로 공유하지 않는다.

| 시험 범위 | 확인 결과 |
|---|---|
| 별도 IN의 시험 네임스페이스: 최초 등록 | 실제 ESP가 AE·alert/status CNT·ACP·SUB를 자동 생성. 신규 ACP의 소유자 63, 엔진 1, 관리자 35 및 소유자 pvs 63 확인 |
| 동일 작업자 재등록 | AE·CNT·SUB·ACP RI, 기존 ACP 정책, SUB 설정과 시험 그룹 참조 유지 |
| poa 변경 | 이전 주소를 모의 설정한 뒤 현재 ESP 주소로 갱신. 실제 하드웨어 재부팅으로 DHCP 주소가 바뀐 경우에도 갱신 확인 |
| poa PUT 실패 | 시험 AE에서 PUT을 403으로 거부하자 실제 펌웨어가 등록 성공으로 처리하지 않고 재시도. 시험 정책은 이후 복구 |
| SUB 없는 시험 CNT의 권한 | Criskengine CREATE 201/2001. 엔진 RETRIEVE·DISCOVERY와 비인가 Origin의 RETRIEVE·CREATE는 403/4103. 소유자 조회 허용 |
| 운영 펌웨어 적용 | 적용 직전·직후 및 최종 조회의 현재 AE·CNT·SUB·ACP RI와 기존 ACP/SUB 설정 유지. heartbeat의 새 CIN 생성 확인 |
| 운영 그룹 연결 | 최신 worker alert RI를 다시 조회하고, 기존 두 멤버와 macp를 보존하며 작업자를 별도로 추가. 최종 cnm=3 및 참조 유지 확인 |
| 실제 경보 | 실제 레이더·RiskEngine·그룹·작업자 SUB 경로에서 WARNING·DANGER·SAFE 수신과 모드 전환 확인. 사용자가 부저·LED의 실제 반응을 확인 |

시험 네임스페이스는 Pi의 기존 별도 IN-CSE에 생성했다. 독립 호스트나 새 독립 DB를 구축한 시험은 아니다. 운영 경보 그룹과 분리된 시험 리소스이며, 시험 AE와 그룹은 정리했다. 운영에 임의 SAFE CIN이나 직접 SAFE/무음 명령을 보내지 않았고, 관찰한 SAFE는 실제 엔진 결과다.

구형 삭제형 펌웨어의 승인된 리셋 구간에서는 worker alert RI가 최초 점검 때와 달라졌다. 따라서 작업 시작 시점의 RI를 전체 과정에서 보존했다고 주장하지 않는다. 새 펌웨어 적용 이후의 현재 RI 보존을 확인하고 그 최종 RI를 그룹에 연결했다. 삭제된 과거 RI의 동일 복원도 보장하지 않는다.

## 유지한 정책 및 후속 항목

- 기존 운영 ACP는 사용자 결정에 따라 보존했다. 당시 기존 엔진 권한은 35였으며, 새 펌웨어만으로 기존 정책이 1로 바뀌었다고 해석하지 않는다.
- alert/status는 여전히 ACP를 공유한다. 신규 정책도 엔진의 CREATE가 status에 적용되므로 리소스별 최소 권한을 완료한 상태가 아니다. 기존 서비스와 status 소비자의 권한을 확인한 후 ACP 분리를 별도로 검토한다.
- 자동 등록과 그룹 가입은 별개다. 펌웨어에 자동 그룹 가입 기능을 추가하지 않았다.
- UNKNOWN에서 작업자 부저의 기존 무음 정책은 유지한다. UNKNOWN 수신이 SAFE 로그와 mode 0으로 나타나는 표현·내부 상태 구분은 [별도 후속 항목](worker-unknown-follow-up.md)이다. UNKNOWN을 자동으로 정상으로 해석하지 않는다.
- 장기 안정성, 전체 시스템 재부팅 복구 및 산업안전 성능을 검증한 결과는 아니다.

## 이후 Pi 작업과의 경계

작업자 시험과 별도로 Pi에서 엔진·Vision·IPE 권한을 축소했고, IPE는 `CmecIPE`, 이력 브리지는 `Cbridge`로 MN을 조회하도록 변경했다. MEC 컨테이너 재시작 정책과 별도 복구 확인은 [Pi 운영 기록](pi-acp-mec-20261123.md)을 참고한다. 이 문서의 실장비 검증 결과와 이후 Pi 변경의 검증 범위를 구분한다.
