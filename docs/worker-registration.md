# 작업자 ESP 등록과 재사용

`esp8266/led_server/worker_node.ino`는 부팅 및 등록 재시도 때 기존 AE를 삭제하지 않는다. AE가 없으면 생성하고, 생성 POST가 409이면 현재 ESP IP의 `http://<ESP_IP>:80/notify`로 `poa`를 PUT한다. PUT이 HTTP 200이 아니거나 조회 결과의 AE-ID 또는 `poa`가 예상과 다르면 등록 실패로 처리한다. 연결된 상태에서는 10초 간격으로 재시도한다.

CNT와 SUB도 생성 POST의 409를 재사용 후보로만 처리하고 실제 리소스를 조회한다. 기존 CNT의 `acpi`를 바꾸지 않는다. 기존 SUB에 자기 AE-ID 수신처, CIN 생성 이벤트(3), `nct=1`이 없으면 삭제·재생성하지 않고 등록을 중단한다. 등록 완료 전 status CIN 생성도 성공해야 한다. 기존 리소스의 RI와 현재 정책은 시리얼 로그에서 확인할 수 있다.

## 신규 ACP와 기존 정책

신규 `acp-worker01`의 `pv`는 다음과 같다.

| Origin | acop |
|---|---:|
| Cworker01 | 63 |
| Criskengine | 1 (CREATE) |
| CAdmin | 35 (기존 운영 권한) |

신규 ACP의 `pvs`는 기존처럼 소유자 `Cworker01`의 63이다. 기존 ACP를 만난 경우 GET으로 `pv`·`pvs`를 보고하며 변경하지 않는다. 409가 기존 정책의 갱신을 뜻하지 않는다. ACP 생성 또는 조회에 실패하면 ACP 없이 CNT를 만드는 대신 등록을 실패 처리한다.

**alert와 status는 여전히 같은 ACP를 사용한다.** 따라서 신규 정책의 엔진 CREATE 권한은 status에도 적용되며 리소스별 최소 권한을 완료한 상태가 아니다. 기존 운영 ACP의 엔진 권한이 35라면 펌웨어 업데이트만으로 1이 되지 않는다. status 소비자와 필요한 권한, 자동 등록·SUB 동작을 확인한 후 기존 `acpi`, 연결된 모든 ACP의 `pv`·`pvs`를 백업하고 별도 이전을 진행해야 한다. 다른 앱의 정책이나 소유자 정책을 임의로 제거하지 않는다.

2026-11-23 팀 Pi의 기존 작업자 CNT는 별도 운영 작업으로 ACP를 분리했다. 펌웨어는 기존 CNT의 `acpi`를 덮어쓰지 않는다. 이 설정과 검증 범위는 [Pi 운영 기록](pi-acp-mec-20261123.md)을 참고한다. 위 공유 ACP 설명은 펌웨어가 **새 CNT를 처음 생성할 때** 여전히 적용된다.

## 그룹 가입과 확인

자동 AE 등록과 경보 그룹 가입은 별개다. 이 펌웨어는 `grp-safezone-alarms`를 생성하거나 `mid`를 수정하지 않는다. 신규 작업자는 운영자가 최신 alert CNT RI를 조회해 기존 그룹 멤버를 보존하면서 별도로 연결한다.

재등록 전후 AE·alert/status CNT·SUB·ACP의 RI, SUB의 `nu`·`enc`·`nct`, CNT의 `acpi`, ACP의 `pv`·`pvs`, 그룹의 `mid`·`macp`를 대조한다. 이전 삭제형 펌웨어가 이미 리소스를 재생성했다면 업데이트만으로 과거 RI가 복원되거나 끊긴 그룹 참조가 고쳐지지는 않는다.

## 빌드와 복구

worker와 forklift 스케치는 같은 디렉터리에 있으므로 Arduino 빌드는 별도 `worker_node/worker_node.ino` 스테이징 폴더에서 한다. 최신 worker 파일과 로컬 `secrets.h`만 준비하고 현재 Pi 주소를 로컬 `CSE_HOST`에 설정한다. `secrets.h`, 컴파일된 바이너리, 전체 플래시 백업에는 자격증명이 포함될 수 있으므로 Git에 추가하거나 공유하지 않는다.

사용 보드와 포트를 실제 로그로 식별하고 `esp8266:esp8266:nodemcuv2` 설정을 확인한다. 업로드 전 전체 플래시와 원본 소스, 코어·라이브러리 버전 및 리소스 설정을 저장소 밖에 보존한다. 전체 플래시 복구는 식별한 동일 보드에서 백업 용량·해시를 확인하고 esptool `write_flash 0x0 <원본 전체 플래시>`로 수행할 수 있다. 실제 복원은 별도 승인 아래 진행한다. 이전 삭제형 펌웨어를 복원·재부팅하면 다시 AE와 자식 리소스를 삭제할 수 있으므로 이후 현재 alert RI와 그룹 연결을 다시 확인해야 한다. 설정 JSON만으로 삭제된 RI를 그대로 복구할 수 있다고 보장하지 않는다.

신규 등록, 동일 작업자 재등록, 잘못된 이전 `poa`의 갱신, PUT 거부 시 등록 실패·재시도, 권한 허용·거부는 먼저 운영 그룹과 분리한 시험 네임스페이스에서 확인한다. 권한 시험 CIN은 SUB가 없는 시험 CNT에만 생성한다. 운영 경보 확인은 실제 레이더 입력과 엔진 출력을 대조하며 임의의 SAFE를 기록하지 않는다.

UNKNOWN에서 작업자 부저의 기존 무음 동작은 이번 변경에서 유지한다. SAFE와 UNKNOWN의 내부 상태·로그 구분은 [별도 후속 이슈](worker-unknown-follow-up.md)이며, UNKNOWN을 자동으로 정상으로 해석하지 않는다.
